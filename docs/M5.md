# M5 — validation and optimization

M5 closes the research.md §9 roadmap: full-matrix validation (fuzz + soak
+ concurrency + preemption), performance hardening of the transfer and
hash paths, a machine-readable support matrix, and the version-shim /
head-to-head harnesses. Source changes are made locally and rsynced to
the GPU checkout before testing (same workflow as M1-M4).

## Performance hardening

1. **Pitched 2-D copies** (`PageCopy2DOp` + `plan_batch` in
   `omnikv/transfer/engine.py`): op planning first coalesces fully
   contiguous runs, then folds every regular stride pattern into one
   `cudaMemcpy2DAsync`. This is the cross-block merging the M3 audit
   showed plain coalescing cannot do — store slots are block-major while
   layer-compact engine pools are layer-major, so a B-block × L-layer
   save submits as ~B pitched copies (height L) instead of B×L memcpys,
   and a load with consecutive GPU blocks and consecutive store pages
   submits as ~L pitched copies (height B). Folding only ever happens on
   *observed constant strides on both sides*, so the planned batch is
   byte-equivalent by construction (unit-tested by interval coverage;
   the GPU bench re-verifies byte equality after real copies).
2. **Shared pinned scratch slots** (`_Runtime.pinned_scratch`): the
   conversion path and the L1 read-back gate no longer pay a
   `cudaHostAlloc` (`torch.empty(pin_memory=True)`) per call — ms-scale
   each. Two named slots ("convert"/"verify") so a read-back buffer
   growth can never free memory that live conversion source pointers
   still reference.
3. **Hash-path micro-optimization** (`omnikv/keys.py`): the token stream
   is packed once per call (one C-level `struct.pack`) and each block
   hashes one memoryview slice instead of one Python
   `int.to_bytes`/`update` pair per token. The packed byte stream is
   identical to the M1-M4 encoding, so block hashes and store keys are
   unchanged (unit-tested against the per-token reference). Chains are
   also *extendable* (`extend_block_hashes`), and the connector now
   memoizes per-request chains across scheduler re-queries (the `None`
   re-query contract fires on every step while saves are in flight) and
   reuses them at `request_finished` time; chains are dropped on request
   completion and GC'd with the same 100-step horizon as lookup contexts.

## Silent-corruption path found and closed

Building the golden-offset fuzz surfaced a real latent adapter bug:
**block-outermost layouts (BLNHC/BLHNC/BHLNC) with kernel-block splits
(ratio > 1)**. In those layouts a manager block's kernel rows sit `L*row`
apart in the pool, so its page is *not* one contiguous run — but
`LayerAddress`'s single-run per-block addressing (`manager_stride =
ratio*stride(0)`) claimed it was, and would have copied interleaved bytes
from neighbouring blocks with no error. Registration now fails closed
for that combination (`RegistrationError`, unit-tested for all three
layouts; layer-compact layouts with splits remain supported — their
kernel rows are contiguous within a layer and this is asserted).

This is exactly the class of bug research.md §10's fuzzing spec targets
("randomized layout fixtures → descriptor → golden model of expected
byte offsets; any mismatch is an adapter bug").

  remote data disk; skipped with a note if the install fails.

## Head-to-head methodology

Identical prompt workload (8 warmed families; measured phases of 32
requests at hit rates 0/50/90 %; greedy decoding; `enforce_eager`) is run
through four configurations: no cache, OmniKV, native prefix cache, and
LMCache (in-tree connector, CPU offload; a missing `lmcache` package is
recorded, never hidden). The FlexKV control runs the same workload
generator inside the audited legacy checkout env (vLLM 0.10.1.1) and is
reported as a *configuration-level* comparison — the engine version
difference is stated alongside the numbers, per the project rule of
publishing wins and regressions honestly. Single-run numbers are smoke
measurements, not statistical claims.

## Support matrix

`docs/support_matrix.json` is the machine-readable support matrix
(research.md §9 M5 deliverable). `tests/unit/test_support_matrix.py`
enforces that it covers every `StateKind` and layout family with
legend-declared statuses, that every entry carries evidence or notes,
that the recurrent no-go and the block-outermost/kernel-split rejection
stay recorded, and that the tracked `FORMAT_VERSION` matches the code —
so "the matrix is accurate" is a tested invariant, not a promise.
